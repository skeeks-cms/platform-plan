# Технический проект SkeekS AI

Версия для обсуждения от 17.11.2026. Цель и этапы продукта описаны в [плане направления](ai.md). Ниже предложены границы поставки и условия приёмки. Названия новых пакетов рабочие.

## Что поставляем

| Компонент | Где устанавливаем | За что отвечает |
| --- | --- | --- |
| `skeeks/cms-ai`, Composer | Каждая участвующая установка SkeekS CMS, включая собственную CRM | Подключение к сервису, чат сотрудника, история сообщений, права участника чата, контекст карточки, уточнения, подтверждения и ссылки на результат |
| `skeeks/cms-ai-service`, Composer | Центральная CRM поставщика | Услуга и её AI-ресурсы, реестр подключений, выдача и отзыв доступа, публичный HTTPS API, выбор профиля, журнал запусков, лимиты и учёт |
| `skeeks-ai-runner`, приложение Node.js | Сервер исполнения ИИ | Адаптеры движков, изолированный запуск, продолжение сессии, запрос разрешённого инструмента, события выполнения и сведения о расходе. Для пилота один адаптер Codex SDK |

Собственная CRM играет обе роли. В качестве первого потребителя она использует тот же клиентский пакет и протокол, которые получит клиентская установка. Библиотеки конкретной модели устанавливаются на сервере исполнения. Второй адаптер добавляется в то же приложение, когда появится второй движок.

### Что осталось для второго движка

Обновление от 21.11.2026. Вместо назначения тестового чата вручную сотрудник выбирает доступный профиль при создании. Сайт сохраняет выбор, сервис проверяет доступ сотрудника. Проверено повторное открытие двух независимых чатов Codex и Claude. Ограничения тестового подключения VClaude сохраняются.

На стенде 21.11.2026 выделен общий интерфейс шага. Существующие привязки Codex перенесены по паре «чат — движок». Сверены все прежние сессии. Контрольный чат после перезапуска вспомнил фразу, полученную до изменения. Создание чата также проверено. Договор адаптера описан в умении разработки пакетов, в разделе `references/ai-engine.md`.

Реализовать второй адаптер и проверить оба движка из одной версии панели. В одном чате сотрудник прикладывает файл, задаёт вопрос по нему, меняет движок и продолжает разговор по прежним сообщениям. Из карточки компании создаёт задачу после подтверждения и получает рабочую ссылку. Приёмка также проверяет сохранение ID чата и истории, изоляцию сотрудников, отказ при недостаточных правах и отсутствие повторной записи при смене движка.

21.11.2026 владелец выбрал Claude Agent SDK вторым движком. На стенде Codex обслуживает обычные чаты, Claude через VClaude подключён к отдельному тестовому чату владельца. Через панель проверены чтение статуса черновика и продолжение сессии после повторного открытия. Для испытания ограничены каталог и состав данных, отправляемых посреднику. Для прямого подключения подготовлен отдельный профиль. Личный вход, запись в CRM через Claude и перенос контекста между поставщиками остаются для отдельной проверки.

## Разбор пилота и пересмотр архитектуры — 24.11.2026

По поручению владельца пилот проверен на стенде. Ниже — состояние кода и предложения по архитектуре. Предложения ждут решения владельца, прежние решения пока действуют.

### Состояние пилота

- Сквозной сценарий работает: Codex нашёл компанию, после подтверждения создал одну задачу и вернул её номер. Ссылки на задачу в ответе нет.
- Пакеты `cms-ai`, `cms-ai-service` и `skeeks-ai-runner` пока не хранятся в системе контроля версий. Подключение к стенду не зафиксировано в репозитории проекта. Выпускать и проверять их в таком виде нельзя.
- Оркестратор пилота — процесс Node. Он держит вход сотрудника, сессии, цикл вызовов инструментов, подтверждения и ход работы в памяти. PHP-часть центрального сервиса пока содержит один инструмент создания задачи.
- Панель сайта синхронно ждёт сервис, а сервис внутри этого ожидания обращается к сайту. При открытии чата с несколькими снимками заканчиваются обработчики PHP, загрузка файлов и создание чата падают по тайм-ауту.
- Перезапуск сервиса завершает сеансы всех сотрудников и регистрирует новый OAuth-клиент.
- Даже одношаговый вопрос уходит в фоновую очередь, ответ приходит за 30–60 секунд.
- Профиль Claude через посредника не получает списки разделов и публикаций, на простой вопрос о содержимом раздела ответа нет.
- Агент не знает устройство сайта: на вопрос о публикациях раздела смотрит только элементы и не видит подразделы.

### Предлагаемые границы

| Компонент | Отвечает за | Состояние |
| --- | --- | --- |
| `cms-ai`, сайт | Панель, вход сотрудника, контекст карточки, обращение к API v1 центрального сервиса без ожидания внутри запроса: отправил сообщение, получил номер запуска, читает события | Запусков не хранит, историю может кешировать |
| Инструменты сайта (`cms-mcp` и доменные пакеты) | Чтение и изменение данных, права, защита от повторной записи | Как сейчас. Защита от повторного создания задачи — в инструменте задач, а не в сервисе ИИ |
| `cms-ai-service`, центральная CRM | Аккаунты, услуги, подключения, API v1, чаты, запуски и события, подтверждения и остановка, лимиты, очередь через `cms-job` | Единственное место хранения состояния |
| `skeeks-ai-runner`, Node | Адаптеры движков, цикл агента, вызовы REST сайта по выданному доступу, браузер; пишет события в сервис | Своего состояния не хранит, перезапускается без потерь |

Windows-приложение и портал становятся ещё двумя клиентами того же API v1.

### Хранимая лента событий запуска

Предлагается сделать основой выполнения хранимую ленту событий запуска: шаг начат, вызов инструмента, результат, ожидание подтверждения, текст ответа по частям, расход, завершение, ошибка, остановка. Из неё строятся лента действий, интерфейс чата с анимацией шагов, метрики, уведомления, общий чат Windows-приложения и портала, подтверждение и остановка из любого клиента, продолжение после пополнения лимита. Пока ход работы живёт в памяти процесса, эти возможности строить не на чем.

### История чатов хранится в центральном сервисе — решение владельца 24.11.2026

Заменяет решение 21.11.2026 о том, что чат и история принадлежат сайту. Причина: самостоятельный чат без сайта и общий чат Windows-приложения и портала требуют одного места хранения.

- Чаты, сообщения, вложения сообщений, запуски и события хранятся в `cms-ai-service` центральной CRM. Рабочие таблицы: `cms_ai_chat` (владелец, подключение и проект сайта, движок), `cms_ai_run` (запуск по сообщению: ID сообщения для защиты от повторов, статус, движок и модель, место выполнения, ссылка на `cms_job_run`, расход), `cms_ai_run_event` (события запуска с порядковым номером).
- Чат проекта привязан к подключению и сайту. Сайт показывает чаты своего проекта через API v1 и проверяет права сотрудника на сайте. Самостоятельный чат проекта не имеет.
- `cms-ai` на сайте не хранит историю и запуски, допускается только кеш. Память, навыки и общие файлы проекта тоже хранятся в центре — [решение 24.11.2026](#проекты-память-и-общие-файлы--решение-владельца-24112026).
- `cms-job` отвечает за выполнение запуска: попытки, аренду, повтор и отмену. События ИИ в общий пакет очередей не переносятся. Общий минимум ленты можно вынести в `cms-job`, когда она понадобится другим длинным заданиям.
- `skeeks-ai-runner` своей базы не имеет и передаёт события в `cms-ai-service`. Панель сайта, Windows-приложение и портал читают события с позиции после последнего полученного номера и отправляют туда подтверждения и остановку.
- Наша CRM использует тот же API v1, что и клиентские установки.
- Чаты пилота из базы стенда переносятся в центральные таблицы с сохранением ID движковых сессий.

### Проекты, память и общие файлы — решение владельца 24.11.2026

Образец — уровни памяти Claude и Codex для компьютера: общие правила, правила и память проекта, личные предпочтения, история сессии. Решение принято по разбору пилота.

**Как устроено в пилоте 21.11.2026.** Общие правила и навыки SkeekS — файлы `knowledge/` в `cms-ai-service`. «Особенности сайта» и навыки сайта — таблица `cms_ai_project` по сайту, один текст до 12 000 знаков, правит только администратор. Общие файлы — папка `runtime` сайта с индексом версий и инструментами «список, чтение, сохранение». История и вложения — у чата. Недостатки: нет личной памяти сотрудника; агент не может пополнить память, а файлы проекта не попадают в контекст без явного чтения; память и файлы привязаны к сайту, а группы в списке чатов — к проектам CRM, у слова «проект» два значения; папка `runtime` не входит в резервные копии и не переносится.

**Решение.**

- **Проект SkeekS AI** живёт в центральном сервисе. Это подключённый сайт или самостоятельный проект без сайта. Чат относится к одному проекту, агент получает контекст только этого проекта.
- **Слои контекста при запуске**, по порядку: правила SkeekS → правила проекта → память проекта → личная память сотрудника → навыки (общие и проекта) → история чата.
- **Правила SkeekS и общие навыки** — файлы в репозитории `cms-ai-service`, обновляются выпуском пакета.
- **Правила проекта** — текст, который правит администратор проекта; для подключённого сайта — сотрудник с правом управления сайтом.
- **Память проекта** — отдельные короткие факты, а не один текст. Агент предлагает добавить или исправить факт, сотрудник с правом записи подтверждает в чате. У факта видны автор, дата и чат-источник, факт можно изменить или удалить. Пример: «услуги сайта — подразделы раздела /services».
- **Личная память сотрудника** — предпочтения сотрудника, действуют во всех его проектах и видны только ему. Пополняется так же, через подтверждение.
- **Навыки проекта** — отдельные записи с названием, описанием и текстом; в контекст попадает описание, полный текст агент читает при необходимости.
- **Общие файлы проекта** — в хранилище CMS центрального сервиса с версиями, общие для всех чатов проекта и доступные по правам на проект. Личные вложения остаются у чата, перенос в проект — явное действие сотрудника.
- **Проекты CRM** («SkeekS Платформа» и т. п.) — метка для группировки чатов в списке, на память и файлы не влияют.
- Windows-приложение, портал и панель на сайте видят одни и те же проект, память и файлы.
- Перенос пилота: «Особенности сайта» и навыки из `cms_ai_project` становятся правилами и навыками проекта сайта, файлы из `runtime` переносятся в хранилище с сохранением путей и версий.

**Общие файлы перенесены на стенде 24.11.2026.** Файлы и папки проекта, неизменные версии содержимого и журнал изменений хранятся в базе `cms-ai-service`. Изменение нескольких файлов применяется целиком. Есть создание папок, удаление и перенос с проверкой версии. Миграция перенесла файлы пилотной папки с теми же путями и версиями. Права по-прежнему проверяет сайт по доступу к дереву разделов. Проект пока определяется сайтом. В окне SkeekS AI строка «Файлы проекта» открывает файловый менеджер: дерево папок, просмотр страниц, картинок и текста, редактирование, загрузка перетаскиванием, переименование, перемещение и удаление.

**Правила и навыки перенесены на стенде 24.11.2026.** Читает и сохраняет их сервис: «Особенности сайта» и навыки проекта — с проверкой версии и формата навыков, каждая редакция хранится с автором и временем. Правила SkeekS и общие навыки сервис отдаёт из своего пакета. На сайте осталась проверка права администратора. Личная память сотрудника и пополнение памяти агентом ещё не сделаны.

### Предлагаемый порядок

1. Взять три пакета под контроль версий, зафиксировать подключение стенда отдельно от прочих правок проекта.
2. Описать API v1: запуск, события, подтверждение, остановка, повтор с тем же ID сообщения.
3. Завести в центральном сервисе таблицы чатов, запусков и событий; перенести на них текущий пилот без новых возможностей; панель перевести на чтение событий.
4. После этого — интерфейс чата по образцу Claude Code desktop ([решение 24.11.2026](ai.md#привычный-интерфейс-чата)), затем второй движок и управление сайтом.

**Этап 1 выполнен на стенде 24.11.2026.** Пакеты взяты под контроль версий: публичные репозитории `skeeks-cms/cms-ai`, `skeeks-cms/cms-ai-service`, `skeeks-cms/skeeks-ai-runner`. Миграции чатов перенесены в `cms-ai-service`, добавлены запуски и события. Каждое сообщение — запуск в очереди `cms-job`; доступ к REST выпускает установка на один час, без интерактивного входа и регистрации клиентов. Исполнитель не хранит состояния, пишет ход работы событиями и останавливается по запросу между шагами. Панель читает события и отдаёт файлы сама. Проверено: ответ с лентой шагов, создание задачи после подтверждения (одна задача), отказ без изменений, остановка в очереди и во время работы, новый чат только с первым сообщением, чат с 11 снимками открывается за доли секунды, чат Claude через новый исполнитель. Договор — умение, `references/ai-engine.md`. Ответы профиля VClaude по спискам остаются неверными — этап 3.

## Центральная CRM и модель данных

- **Услуга** использует существующий `CmsDeal`. Коммерческие условия, участники и срок обслуживания живут в карточке услуги. Центральный пакет регистрирует доступ к AI как ресурс услуги через `dealAccess.resourceProviders`. Сайт, уже входящий в услугу хостинга, связывается с подключением как разрешённая цель и сохраняет своего владельца.
- **Подключение** связывает одну установку с ресурсом услуги. В записи хранятся состояние, идентификатор, разрешённые цели и профиль. Предлагаем для пилота одно подключение на установку. Общий бюджет услуги может покрывать несколько подключений.
- **Запуск** принадлежит подключению и чату, содержит автора поручения, уникальный ID сообщения, текущий статус и фактический движок. Историю исполнения и повторы фонового задания ведёт существующий `cms-job`. Центральный пакет регистрирует тип задания и его обработчик.
- **Операция и расход** связаны с запуском. Журнал различает обращения к API, пользовательские поручения, вызовы инструментов и показатели модели. При параллельных запросах резерв бюджета делается атомарно перед запуском. После завершения резерв сверяется с фактическим расходом, при отсутствии данных расход помечается как неизвестный. Правила выставления счетов определяются при выборе тарифа.

## Клиентская установка

Администратор включает компонент и привязывает его к выданному подключению. Для пилота предлагается отзываемый секрет установки, который хранится в серверной конфигурации. Сотрудник открывает чат из CRM или карточки сайта под своей обычной учётной записью. Клиентский backend проверяет доступ к чату и карточке, хранит пользовательскую историю и отправляет текст и необходимый контекст в центральный сервис. Повторное открытие чата восстанавливает сообщения и статус по идентификатору запуска.

Доступ установки к AI и право сотрудника выполнить действие проверяются отдельно. Центральный сервис определяет установку по её учётным данным. Для обращения к целевой CRM или сайту используется отдельная ограниченная авторизация REST/MCP с привязкой к цели и инициатору. Целевая система проверяет актуальные права при записи. Для пилота требуется проверить делегированный вход сотрудника и отзыв его прав между постановкой и исполнением задания. История чатов, файлы и результаты доступны в пределах установки и прав участников.

## Обмен и выполнение

Предлагаемый внешний контракт — HTTPS API v1 центрального сервиса. Клиент отправляет сообщение с ID чата и уникальным ID сообщения, получает ID запуска. Затем читает события после последнего полученного номера, отвечает на уточнение или подтверждение и может отменить запуск. Повтор того же сообщения возвращает существующий запуск. Каждая операция, включая чтение событий, проверяет принадлежность подключения. Первый интерфейс может опрашивать события, поэтому результат доступен после закрытия вкладки.

Обработчик `cms-job` передаёт серверу исполнения ID запуска, профиль, контекст и список разрешённых действий. Для внутреннего пилота подходит вызов фиксированной команды по ограниченному SSH-ключу с JSON через стандартный ввод. Для каждой попытки приложение сверяет ID запуска и состояние сохранённой сессии. Адаптер возвращает общие события: начало, запрос инструмента, результат, ожидание пользователя, завершение или ошибка. Идентификатор сессии движка хранится отдельно от ID чата. Движку доступны только инструменты текущего сценария и цели.

Вызовы целевого REST/MCP выполняет контролируемый обработчик инструментов на стороне сервиса исполнения. Он получает привязанные к запуску полномочия, сверяет цель и разрешённую операцию. Для продолжения после уточнения хранится состояние запуска. Новый ответ сотрудника принимается только для ожидающего чата и предложенного выбора. При отмене уже выполненные действия остаются в журнале.

## Первый сквозной сценарий

1. Сотрудник пишет «Создай по этой компании задачу обновить контакты». Из карточки берётся подтверждённая ссылка на компанию. Если запрос пришёл из общего чата, агент ищет компанию через REST в пределах прав сотрудника.
2. При нескольких совпадениях чат предлагает видимые варианты. Для поручения по услуге проверяется, что услуга относится к выбранной компании. Затем выполняется поиск похожих открытых задач.
3. Исполнение опирается на существующий сервис рабочих задач и операции семейства `cms_task`. Перед созданием проверяются обязательные поля, права сотрудника и подтверждения, которые запросил API. На целевой стороне ключ операции и ID созданной задачи требуется фиксировать в одной транзакции. Если текущий инструмент этого не обеспечивает, в пилот входит узкое расширение целевого обработчика. Это позволяет безопасно повторить запрос после потери ответа.
4. Задача считывается обратно. Сотрудник получает в чате номер, ссылку и компанию. После обновления страницы ответ доступен в том же чате.

## Порядок реализации и приёмка

1. Внутренний пилот на стенде. Подключить нашу CRM как обычного потребителя, один движок и инструменты поиска и создания задачи. Проверить неоднозначную компанию, недостаточные права, обрыв после записи и повтор сообщения. Для одного поручения создаётся максимум одна задача.
2. Первая внешняя установка. Выдать и отозвать подключение, заменить секрет, проверить изоляцию двух клиентов и общий лимит при одновременных запросах. До коммерческого запуска определить тариф, хранение данных и способ оплаты услуг поставщиков моделей.
3. Чат карточки сайта. Подключить отдельную цель REST/MCP, создать или изменить черновик, проверить состояние и ссылку, публиковать при разрешённом поручении.
4. Подключить второй движок через тот же контракт запуска. В сценариях MAX и Telegram переиспользовать `cms-communication`, штатные проверки и отправку. Передача диалога сотруднику должна предотвращать отправку уже подготовленного автоответа.

К обсуждению перед пилотом остаются названия пакетов, способ делегирования прав на целевой системе, место хранения и срок жизни сессий движка, а также объём истории, передаваемой исполнителю. Готовность инфраструктуры Codex уже проверена. Готовность интеграции оценивается по первому сквозному сценарию.

## Постоянная рабочая папка проекта

Место хранения заменено 24.11.2026: [общие файлы проекта хранятся в центральном сервисе](#проекты-память-и-общие-файлы--решение-владельца-24112026), общий доступ из чатов проекта сохраняется. Сотрудник сохраняет туда материалы проекта: макеты, исходники страниц и стили. Открыв другой чат этого сайта, сотрудник с соответствующими правами может продолжить работу с этими файлами. Привязка ведётся по установке и сайту и сохраняется при смене движка.

Личные вложения остаются у чата. Перенос в общий проект — явное действие сотрудника с правом записи. Для временных файлов каждый запуск получает отдельную папку cms-job. Готовые страницы и опубликованные ресурсы сохраняются средствами целевой CMS.

Первоначальные условия приёмки: сохранить макет из одного чата, использовать его из другого с проверкой прав, провести две параллельные сборки и открыть сохранённый макет после очистки обеих рабочих папок.

При закрытой вкладке воркер штатно остановили между шагами после файла и первой страницы. Новый процесс продолжил тот же запуск. В истории сохранился один итог с четырьмя рабочими ссылками. Эта проверка касается временной папки запуска и сохранения результатов.
